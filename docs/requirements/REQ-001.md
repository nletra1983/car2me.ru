# REQ-001 — Сквозной сценарий на сайте

**Статус:** draft  
**Контур:** as-is (гипотеза лендинга на этапе теста)

## Поведение

- Пользователь переходит на сайт по ссылке без якоря
- Пользователь принимает куки ([REQ-003](REQ-003.md))
- Пользователь изучает информацию на лендинге
- Пользователь просматривает юридическую и контактную информацию ([REQ-007](REQ-007.md))
- Пользователь читает подробный кейс (опционально)
- Пользователь смотрит пример отчёта (опционально)
- Пользователь оплачивает услугу ([REQ-004](REQ-004.md))
- Пользователь заполняет форму ([REQ-005](REQ-005.md))
- Система информирует пользователя о сроках получения ответа (в рамках [REQ-005](REQ-005.md) / [REQ-006](REQ-006.md))

## Acceptance criteria

> **Характер AC:** это чеклист гипотезы лендинга (блоки убеждения), а не жёсткое «система делает X». На этапе теста гипотез — ок. Для автотестов позже дробить на отдельные проверяемые REQ/кейсы.

- [ ] При входе на сайт пользователю доступна следующая информация (порядок и состав могут меняться по результатам тестов):
  1. в чём его выгода
  2. почему это является выгодой для него
  3. что есть наш продукт
  4. почему именно этот продукт ему нужен
  5. почему покупать именно у нас
  6. почему нужно покупать сейчас
  7. почему по этой цене
  8. социальные доказательства
  9. пример
  10. порядок взаимодействия для получения услуги
  11. обязательная юридическая информация ([REQ-007](REQ-007.md))

- [ ] Пользователю доступны следующие функциональные действия:
  1. переход к оплате
  2. переход к заполнению формы
  3. переходы по ссылкам для изучения юридических документов
  4. просмотр примера отчёта
  5. просмотр кейса или кейсов (= социальных доказательств)
